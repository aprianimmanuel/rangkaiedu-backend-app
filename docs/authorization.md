# Rangkai Edu - Authorization System

## Overview

The Rangkai Edu authorization system implements role-based access control (RBAC) using JWT tokens with embedded role claims and custom middleware for route protection. This document explains how the authorization system works, including JWT structure, middleware usage, and role-based access control implementation.

## JWT Token Structure with Role Claims

JWT tokens generated by the authentication system include role claims in their payload. This allows the authorization middleware to determine a user's permissions without additional database queries.

### Token Payload Structure

When a user successfully authenticates via the OTP flow (`/verify-otp` endpoint), a JWT token is issued with the following payload structure:

```json
{
  "sub": "user-uuid",
  "email": "user@example.com",
  "phone": "+6281234567890",
  "role": "student",
  "iat": 1729000000,
  "exp": 1729086400,
  "iss": "rangkai-edu-backend",
  "aud": "rangkai-edu-frontend"
}
```

### Role Claim Details

The `role` claim contains one of the following values:
- `admin` - System administrators with full access
- `teacher` - Educators with access to teaching resources
- `student` - Learners with access to course materials
- `parent` - Guardians with access to student progress information

### Additional Security Claims

The JWT tokens also include additional security claims:
- `iss` (Issuer) - Identifies the principal that issued the JWT (`rangkai-edu-backend`)
- `aud` (Audience) - Identifies the recipients that the JWT is intended for (`rangkai-edu-frontend`)

### Token Generation

Tokens are generated in both the [`VerifyOTPHandler`](controllers/auth_controller.go#L254) and [`LoginHandler`](controllers/auth_controller.go#L347) functions in the authentication controller. The role is extracted from the user's database record and included in the JWT claims:

```go
// Generate JWT
claims := jwt.MapClaims{
    "sub":   userID,
    "email": email,
    "phone": phone,
    "role":  role,
    "iat":   time.Now().Unix(),
    "exp":   time.Now().Add(24 * time.Hour).Unix(),
    "iss":   "rangkai-edu-backend", // Issuer
    "aud":   "rangkai-edu-frontend", // Audience
}
```

## Middleware Usage for Route Protection

The authorization system uses two primary middleware functions to protect routes:

### AuthRequired Middleware

The [`AuthRequired`](middleware/auth.go#L21) middleware validates JWT tokens and extracts user information:

```go
// Apply to routes that require authentication
protected := r.Group("/api/protected")
protected.Use(AuthRequired())
```

This middleware:
1. Extracts the JWT token from the `Authorization: Bearer <token>` header
2. Validates the token signature and expiration
3. Extracts user claims (including role) from the token
4. Stores user information in the Gin context for use by subsequent handlers

### RoleRequired Middleware

The [`RoleRequired`](middleware/roles.go#L19) middleware checks if the authenticated user has a specific role:

```go
// Apply to routes that require a specific role
admin := protected.Group("/admin")
admin.Use(RoleRequired(RoleAdmin))
```

### RolesRequired Middleware

The [`RolesRequired`](middleware/roles.go#L50) middleware allows access to users with any of the specified roles:

```go
// Apply to routes that allow multiple roles
content := protected.Group("/content")
content.Use(RolesRequired(RoleAdmin, RoleTeacher))
```

## Role-Based Access Control Implementation

The RBAC system is implemented through a combination of JWT claims and middleware functions.

### Role Definitions

Roles are defined as constants in the middleware package:

```go
type Role string

const (
    RoleAdmin   Role = "admin"
    RoleTeacher Role = "teacher"
    RoleStudent Role = "student"
    RoleParent  Role = "parent"
)
```

### Access Control Logic

1. **Authentication Check**: The `AuthRequired` middleware ensures only valid JWT tokens can access protected routes
2. **Role Verification**: The `RoleRequired` and `RolesRequired` middleware check the user's role against allowed roles
3. **Access Decision**: Access is granted only if both authentication and authorization checks pass

### Error Handling

The middleware returns appropriate HTTP status codes:
- `401 Unauthorized` - Missing or invalid JWT token
- `403 Forbidden` - Valid token but insufficient role permissions

## Protected Endpoints and Required Roles

### Example Protected Routes

Here's how different types of routes are protected in the system:

#### Public Routes (No Authentication Required)
```go
// Authentication endpoints
r.POST("/api/auth/register", controllers.RegisterHandler)
r.POST("/api/auth/send-otp", controllers.SendOTPHandler)
r.POST("/api/auth/verify-otp", controllers.VerifyOTPHandler)
```

#### Authenticated Routes (Any Valid User)
```go
// Profile information accessible to all authenticated users
protected := r.Group("/api/protected")
protected.Use(AuthRequired())
{
    protected.GET("/profile", func(c *gin.Context) {
        // Handler implementation
    })
}
```

#### Admin-Only Routes
```go
// Administrative functions
admin := protected.Group("/admin")
admin.Use(RoleRequired(RoleAdmin))
{
    admin.GET("/users", func(c *gin.Context) {
        // Only accessible by admin users
    })
}
```

#### Multi-Role Routes
```go
// Content management accessible by admins and teachers
content := protected.Group("/content")
content.Use(RolesRequired(RoleAdmin, RoleTeacher))
{
    content.POST("/lessons", func(c *gin.Context) {
        // Accessible by both admins and teachers
    })
}
```

## Implementation Best Practices

### Security Considerations

1. **Token Expiration**: JWT tokens expire after 24 hours to limit the impact of token compromise
2. **Role Validation**: Roles are validated at the middleware level before reaching business logic
3. **Secure Storage**: OTPs are stored hashed in the database with expiration times

### Performance Optimization

1. **Claim-Based Authorization**: User roles are embedded in JWT tokens, eliminating the need for database lookups during authorization
2. **Middleware Chaining**: Middleware functions are designed to be chained efficiently
3. **Context Propagation**: User information is passed through the Gin context to avoid redundant parsing

### Error Handling

The middleware provides clear error messages for different authorization failure scenarios:
- Missing Authorization header
- Invalid token format
- Expired or invalid JWT
- Insufficient role permissions

## Usage Examples

### Protecting a New Route

To protect a new route with role-based access control:

```go
// Create a protected group
protected := r.Group("/api")
protected.Use(AuthRequired())

// Add role-specific subgroups
adminRoutes := protected.Group("/admin")
adminRoutes.Use(RoleRequired(RoleAdmin))

teacherRoutes := protected.Group("/teaching")
teacherRoutes.Use(RolesRequired(RoleAdmin, RoleTeacher))

// Define your endpoints
adminRoutes.GET("/settings", getAdminSettings)
teacherRoutes.POST("/assignments", createAssignment)
```

### Accessing User Information in Handlers

Handlers can access user information from the Gin context:

```go
func userProfileHandler(c *gin.Context) {
    userInterface, exists := c.Get("user")
    if !exists {
        c.JSON(http.StatusUnauthorized, gin.H{"error": "User not found in context"})
        return
    }
    
    user, ok := userInterface.(middleware.UserContext)
    if !ok {
        c.JSON(http.StatusInternalServerError, gin.H{"error": "Invalid user context"})
        return
    }
    
    // Use user.ID, user.Email, user.Phone, user.Role as needed
    c.JSON(http.StatusOK, gin.H{
        "id":    user.ID,
        "email": user.Email,
        "phone": user.Phone,
        "role":  user.Role,
    })
}
```

This authorization system provides a robust, secure, and flexible way to control access to API endpoints based on user roles while maintaining good performance through JWT-based claims.
